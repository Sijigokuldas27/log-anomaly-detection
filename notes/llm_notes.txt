what i saw
- rag helps cause and next step, the runbook gives it real things to check
- rag summary is little worse, sometimes copies runbook words that dont fit the block
- without rag it says high almost every time (26 of 30). rag is more medium but almost never low
- when logs have clear error msg (socket timeout, connection reset, replication timed out)
  both answers are good. blocks 11, 27, 30 got 7 of 8
- when problem is small or there is no problem, it makes up a failure:
  empty packet blocks -> says pipeline failed, but block was stored on 3 and verified
  redundant report / extra copy removed -> says replication failed or delete failed
  sometimes says verification failed when the log says verification succeeded
- normal blocks: rag is much worse (0.17). the runbook notes are about failures,
  so it finds one even when there is none
- prompt says "our model said this block is an anomaly" -> llm believes it and never says
  the block looks fine. this is a big reason for wrong answers on normal blocks
- very short block (only allocate + 1 receiving): it cant see missing steps, only reads what is there,
  so it guesses wrong
- delete error type (blocks 13, 20, 28) gives almost same answer every time, so temperature 0 is stable
- sometimes answer contradicts itself (replication failed, but block was replicated)
- many hdfs blocks labeled anomaly look harmless in the logs (empty packet, redundant report).
  so part of the problem is the label, not only the llm

limits
only 30 blocks, only 6 normal, so normal number is not strong
only one person rated (me)
not fully blind: rag answers sometimes use runbook words so i could guess which one is rag
small 3b model, bigger model may do better

tested on 12 rated blocks: all 6 normal + 6 random anomalies, without and with rag
took around 45 min (much slower than before, around 2 min per answer)
model sometimes gave true/false instead of yes/no, fixed in the script

                 normal said normal   anomaly said problem
no rag                6 of 6                1 of 6
rag                   6 of 6                1 of 6

- normal blocks fixed completely, before it made up failures on them
- but now it says almost everything is normal, only caught block 1 (clear exception msg)
- block 27 is real replication timeout, it even wrote "replication timed out" in the summary
  and still said looks normal
- severity mostly "none" now (19 of 24)
- so the 3b model mostly follows what the prompt says, not what the logs show
  old prompt -> finds problem everywhere, new prompt -> finds problem nowhere
- conclusion: llm should only explain, the detector should decide. dont use small llm as second detector
